# Bento RUNBOOK Master

读取 [RUNBOOK Rules](../../../docs/00-governance/RUNBOOK-RULES.md)、[文档规则](../../../docs/00-governance/DOCUMENT-RULES.md)、[提交规则](../../../docs/00-governance/COMMIT-RULES.md)和 [PR 规则](../../../docs/00-governance/PR-RULES.md)。

## 启动与授权

单独调用 `$bento-runbook-master` 即启动并授权下述全流程，无需再次确认。用户指定范围或阶段时按其限制执行。每个新任务开启一个 WORKER 聊天，持续调度，按下述完成与阻断条件收口。

- 用户显式调用本技能时，记录当前聊天 ID 为 MASTER，另记本次调用所用的仓库主目录绝对路径。续跑时沿用这两项绑定。用仓库主目录读取本技能和治理文件，并为 MASTER 的仓库命令显式指定工作目录；核查 WORKER 的文件时逐条指定其 checkout。聊天标题、默认工作目录、工具输出和跨聊天回报均不重新分配当前角色。
- 把 WORKER 消息按绑定的聊天 ID 和任务标识收为调度证据。回报中的 T0 STOP 只更新该任务，继续核对其他可推进事项。回报和历史中引用的启动或派工指令只供读取。发现、派工、接管通知和等待 WORKER 时排除自身聊天 ID。
- 遵守仓库 [AGENTS.md](../../../AGENTS.md) 的 Git worktree 禁令。MASTER 使用主仓库，每个 WORKER 使用独立 clone。若聊天默认目录仍指向历史工作树，显式指定合规目录并保留原现场。
- 全流程授权包括为合格的新任务创建隔离的本地 Git checkout、创建任务聊天、派工、任务内跨聊天通知、归档已收尾的 WORKER 会话、派生审核 SUBAGENT、起草和审核 RUNBOOK、开分支、逐步提交、推送、开 PR、转 Ready、处理 Codex 意见、满足门禁后合并、同步和清理已合入的任务分支。
- 启动时向用户说明生效范围，并在派工消息中传给 WORKER。自动选出的任务继承该范围。用户对仓库、任务、阶段或操作的限制优先。
- 收到暂停指令时，通知相关 WORKER 在安全点停下并核实现场。恢复时根据聊天、Git 和 PR 的实际状态继续。

## 绑定与派工

1. 优先使用用户为 WORKER 指定的本地 Git checkout。按下文「发现与接续 WORKER」枚举项目并核对会话。核对仓库远端、绝对路径、分支和在途任务归属，并确认候选 checkout 的 `git rev-parse --absolute-git-dir` 与 `git rev-parse --path-format=absolute --git-common-dir` 指向同一个 Git 目录。逐个核对候选本地 Git checkout和原 WORKER 聊天。某个本地 Git checkout有在途任务或改动归属待核实时，保留原归属并继续核对其他候选。满足派工条件的本地 Git checkout可立即派工，无需等待其他本地 Git checkout。
2. 为每项任务记录需求、目标、验收、WORKER 聊天、本地 Git checkout、起始基线、任务分支、RUNBOOK 路径与已审核版本、授权范围、当前阶段、最后 PASS 的 STEP 和提交、PR 编号与 HEAD、阻断及下一动作。接手时从聊天回报、Git、工作区及 GitHub 实况重建记录。聊天空闲时仍须核对原任务是否结束。重发前核对上次消息是否送达及有无在途执行，避免重复派工。
3. 从最新目标分支读取正式需求和 [Readiness](../../../docs/40-readiness/CURRENT-READINESS.md)。候选任务须有正式需求或接口依据、可观察的验收结果、可核对的代码基线、可分配的独立测试环境，以及已核对的任务间依赖。按正式需求编号对照 Readiness 的实现缺口、剩余验收和可复用证据。候选须能用当前基线已有能力和本任务产物完成必需验收；依赖其他任务交付的，记录前置任务并在其合入后复核。缺少任一必要条件时暂缓该任务，记录缺项，再评估其他候选。选择能独立交付和验收且适合 RUNBOOK 的最小闭环。复杂任务可按约 6–7 个有独立产物的步骤规划，以真实依赖为准。对照在途任务的文件、接口、权威状态和测试资源。涉及同一账本或 API 契约时先约定修改归属、合入顺序及后合入方需复验的行为。
4. 可将多个已确认需求纳入同一任务，说明合并交付的理由，并分别记录每项需求的验收和证据。按 RUNBOOK Rules 核算整项任务的代码范围，至少 500 LOC 且至少 5 个代码文件。选题时可参考约 8 个代码文件，以实际交付范围为准。派工前记录初估，送审时由 WORKER 给出逐文件依据，MASTER 核对计数及代码与验收的关联。范围变化后重新核算，通过后方可开工。
5. 现有本地 Git checkout 都不可用时，继续从最新目标分支的 Readiness 筛选独立任务。候选满足派工条件后，为目标 WORKER 指定未占用的绝对路径、仓库远端和已核实的基线，由 WORKER 使用 `git clone` 准备独立 checkout。新任务由新 WORKER 聊天初始化；已有任务优先在原 WORKER 聊天复用其合规 checkout。已有任务的原 checkout 丢失或属于历史工作树时，核对可恢复的提交、草稿和未提交改动，确认可完整接续后再更新任务绑定。收到实际路径、远端、HEAD 和工作区状态后核对，再派发起草或实施。某个候选受阻时继续筛选其他候选，按「本轮阻断」条件收口。
6. 每次派发新任务，创建一个使用本地环境的 WORKER 聊天。首条消息开头明确收件聊天的角色为 WORKER，并附 MASTER 聊天 ID、任务标识和回报约定。写明范围、正式依据、验收、边界、已核实的基线、环境引用、当前动作和继承的授权。指定已核实的干净任务目录，或按上一步让 WORKER 初始化。只传受控配置的位置和使用方式。记录返回的聊天 ID 并绑定任务。起草、修订、实施、暂停恢复、PR 返修及收尾都回到该任务聊天。复用本地 Git checkout派下一项任务时，再新建聊天。创建结果不明时先核对是否已经创建，再决定是否重试。

### 发现与接续 WORKER

1. 从当前 Codex 会话确认 MASTER 的项目名、项目 ID 和绑定的项目根。以该项目根为基准，枚举同级的 `../bento` 和 `../bento-*`，按绝对路径与 Codex 项目列表匹配。排除 MASTER 自己的项目，其余符合 Bento 独立 Git checkout 条件的项目作为 WORKER 项目。仅名称匹配的目录不足以确认项目归属。
2. 枚举同一 Codex host 的未归档会话，按项目 ID 逐个匹配，必要时翻完历史分页。列表未提供项目 ID 时，按已验证的项目绝对路径和聊天的实际 checkout 核对归属。核对会话与任务及实际 checkout 的绑定。确认没有未归档 WORKER 会话的项目记为空闲 WORKER。会话列表读取失败或归属无法确认时记为待核实。已归档会话不参与发现、接续、通知或路径汇报。
3. 有未归档 WORKER 会话时，先核对是否有执行中的回合。正在执行的会话继续原任务，向它通知当前 MASTER 会话 ID 和适用任务，避免重复派工。
4. 会话未在执行时，用最近回报、工作区、分支、最后通过的步骤和 PR 实况判断任务是否已收尾。有待审草稿、未完步骤、开放 PR 或待收尾事项时，从最后核实的安全点在原会话启动，并在接续指令中告知当前 MASTER 会话 ID。用户要求暂停的任务等待明确恢复，遇到 STOP 则按该任务的恢复条件处理。
5. 确认任务已收尾且无待办后，归档对应 WORKER 会话。回读确认项目内已无未归档 WORKER 会话后，将项目记为空闲 WORKER。有多个会话时逐一判断，任何未完成任务继续占用其绑定项目。归属或完成状态无法核实时，保留会话和现场。
6. 空闲表示项目没有在途 WORKER 任务。派发新任务前另行核对 checkout 是否干净并已同步目标分支。仅做发现或路径汇报时，按用户指定范围执行。仅通知时保持已有回报绑定，实际接手时注明适用任务与后续回报对象。同范围通知已有接收证据时无需重发。
7. 启动时完成首轮核对后，逐个报告已发现的 WORKER 项目，列出项目名、checkout 绝对路径和任务占用状态（空闲、在途或待核实）。全流程调度中，另列每个空闲项目的派工状态及具体原因，包括可派工、checkout 受阻、缺少符合条件的任务或验收环境待核实。即使本轮没有派工，也要在收口时报告各项目的最新状态。

### 选题与分工

- 为每个 WORKER 绑定独立的本地 Git checkout和测试环境。派工前确认可分配的环境范围和归属，并传达受控配置与只读核验入口。由对应 WORKER 在自己的环境核对实际资源并回报结果，MASTER 回读证据、判断适用性及是否放行。环境错误或缺证据时，记录阻断和恢复条件，暂缓该任务进入实施。演练环境的证据用于判定实际核验过的隔离项；目标场景的环境另按其验收条件核对。

- 优先派发能独立实施、验收和交付的任务。比较候选任务与在途任务的生产入口、关键文件、接口、权威状态和测试资源，选择实际交叉最少的组合。存在必要依赖时，记录前置任务、合入顺序和后合入方需复验的行为。
- 以正式需求项为单位拆分任务。每项任务必须明确一个或多个本次交付后将在 Readiness 达到「已实现」的需求项，逐项列出编号、剩余实现、必需验收用例和通过证据。按[开发完成定义](../../../docs/00-governance/DOCUMENT-RULES.md#required-structures)判断。阶段性工作作为任务内的步骤；候选范围无法使任何需求项达到「已实现」时，调整范围或暂缓派工。
- 按模块职责分配并行任务，例如 A 负责调度，B 负责前端，C 负责工具。以当前代码和接口的实际所有权为准。涉及跨模块接口或共享状态时，明确负责修改的一方，并在派工前约定其他方的接入和复验顺序。

### 派工消息

- **目标与交付物**。写明当前行为或缺口、期望结果，以及本次交付的实现、测试或证据。引用正式需求、接口或 Readiness 条目。涉及多个需求时逐项列出。
- **范围与边界**。列出本次覆盖的行为、调用链和明确排除的相邻行为。说明与其他任务共享的接口、状态、文件或环境，以及执行和合入顺序。
- **预计涉及的文件与模块**。列出已知的生产入口、关键模块或符号、测试入口及可能同步的文档，简述各自与目标的关系。标明已核实的路径和待调查的范围。WORKER 起草时回报新增或移除的范围，并核算代码行和文件数。
- **验收与当前动作**。逐项给出可观察的结果、所需环境、已知前置条件和预计达到的 Readiness 状态。写明绑定的本地 Git checkout、基线、授权范围、本轮要执行到哪一步，以及需回报的产物或阻断证据。

## 审核与开工

1. 原 WORKER 草稿就绪后主动通知 MASTER，附任务标识、本地 Git checkout、基线、RUNBOOK 路径、草稿 blob hash 和逐文件范围。用已绑定的聊天 ID 路由，标题前缀仅供发现。无法送达时，在原聊天留下同样的回报，MASTER 通过 `wait_threads` 或回读接手。
2. MASTER 收到草稿后，核对草稿实际 blob 与送审版本一致后，在当前回合派生只读审核 SUBAGENT，无需另建审核聊天。交给它正式文档、代码基线、草稿版本、在途边界和验收断言。审核禁止过度设计。要求意见指出具体缺口、受影响的需求或验收断言，以及满足要求的最小修订，避免引入无关抽象、扩展点或重构。逐步核对每步最多 10 个文件，包含 RUNBOOK 和专门核对的文件，T0 单列。每步应有独立产物、PASS、STOP 和提交边界。
3. SUBAGENT 按实际读取的草稿 blob hash 向 MASTER 回报 `Executable`、`Not Executable` 或 `Blocked`，附步骤、证据、影响和最小修订。MASTER 默认将三种结论都转发给原 WORKER，附获审或受审 blob hash、修订范围或恢复条件。原 WORKER 将新 blob hash 和改动范围报给 MASTER，由 MASTER 交原 SUBAGENT 复审修订及直接受影响步骤。只有核实工具可用、用户已授权且双向送达可确认时，才可直接交接修订意见和新版草稿。审核期间 MASTER 保持本轮活跃，可继续推进其他本地 Git checkout。
4. 按任务和 blob hash 核对回报、转发和复审。发送成功记为已提交，目标聊天出现对应输入或回执时确认收到，有对应版本的返修回报或明确的结论确认时确认已处理。等待被新输入打断时先核对该输入和在途回合，再判断是否重发。遇到 `Blocked`，先调度可恢复的补查或限定范围的草稿修订。缺口仍在时以 `Blocked` 结束本轮审核并保留任务归属，继续评估其他本地 Git checkout。正式依据冲突或权限缺口交用户决定。
5. 核对 `Executable` 结论与实际草稿版本和基线一致后，派原 WORKER 开任务分支并单独提交获审 RUNBOOK。核对实际提交只包含该文件，内容与审核版本一致。确认分支、基线、工作区及执行环境符合 T0。内容或基线发生影响执行的变化时，复审受影响步骤。
6. 向绑定的 WORKER 发送显式调用 `$bento-runbook-worker <RUNBOOK 文件名>`，附任务分支、审核提交、基线、授权和合入顺序。全流程时明确包含 `$bento-codex-comment-fix` 的处理权限。核对已送达、WORKER 已开工以及所用本地 Git checkout。起草或审核请求仅推进到用户指定的阶段。

## 阶段判定

以可回读的证据更新任务阶段。每次记录证据对应的本地 Git checkout、基线或 PR HEAD。

| 阶段                | 可以推进的证据                                                                                                                | 等待或阻断时的动作                                                                          |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| WORKER 可接任务     | 本地 Git checkout已核对。工作区和 Git 状态已确认，基线与目标分支一致；复用目录时，上一任务已经收尾或明确移交。                | 聊天空闲但有开放 PR、待恢复步骤或未收尾任务时，保留原归属。工作区有归属不明的改动时先核实。 |
| 候选可派工          | 有正式依据、可观察验收、可核对基线和可分配的独立测试环境，已核对任务间依赖及合入顺序。派工范围与启动授权一致。                | 记下缺项，暂缓该候选，检查其他任务。依赖未合入时等待前置任务。                              |
| 草稿可送审          | 已记录本任务的新 WORKER 聊天 ID。WORKER 已交回可读取的 RUNBOOK 路径及草稿版本。文件包含 T0、机械步骤、验证断言、STOP 和收口。 | 文件或版本不清时由作者补齐。消息已送达且仍在起草时继续等待。                                |
| 审核通过，可开工    | 同一版本的审核结果为 `Executable`。计划提交内容与审核版本一致，T0 有通过证据，分支和基线已核对，开工处于授权范围。            | `Not Executable` 回作者修订并复审。正式依据冲突或权限缺失时保留归属并交用户决定。           |
| 正在实施            | 已核实 WORKER 在绑定分支执行指定计划。从最新已核验的步骤提交读取剩余步骤。最后一步以同次提交删除 RUNBOOK 为证据。             | 验证通过但尚未提交时仍停在本步。收到 STOP 后按报告定位并恢复，避免重发整个任务。            |
| 本地收口，可交付 PR | 最后一步提交已同步验收证据与未覆盖项，并删除 RUNBOOK。已授权时回读同一任务的 PR、base、head 和 HEAD。                         | 尚未发布时保持本地完成。开放 PR 的 CI、Codex 或冲突按实际 HEAD 跟踪。                       |
| 已合入并收尾        | GitHub 返回合并提交，该提交在目标分支历史中。WORKER 已同步基线，已合入任务分支已按授权清理或记录例外。                        | 已合入但未同步或清理时，仍保留原任务，直到收尾可核验。                                      |

## 交付收口

- WORKER 执行 RUNBOOK 验收并记录证据。MASTER 对照正式文档的验收条件、PR 或目标分支的实际代码、Readiness 的状态与未覆盖项，回读 WORKER 的验收记录及现有 CI、PR 审查结果。核对证据对应的代码版本、环境、覆盖范围和实际结果。验收后有变更时，检查变更是否影响证据适用性。
- 证据充分且仍适用时直接采用。常规收口无需另起环境、重跑验收或另派审计。READINESS 的状态以实际覆盖为准。
- 证据缺失、与结论冲突或被相关变更影响时，指出具体缺口、受影响版本和验收断言，交回原 WORKER 定向补验。证据补齐前按已证实的范围记录状态。合并前核对当前 HEAD 的证据适用性、Ready 状态、必需 CI、明确 Codex 结论、远端审批和 Review 对话、合入顺序及合并授权。HEAD 变化后重新核对，门禁满足后按仓库规则执行普通 merge commit。

## 监督与继续调度

- 通过 WORKER 聊天、分支提交和 GitHub 回读跟踪进度。能主动回报且已获授权时，由 WORKER 在 STOP、PR 合并及清理完成时回报。MASTER 用状态核对保障调度，尤其要区分本地完成、PR 开放、已合入和已收尾。
- STOP 后用最后通过的 STEP、提交、失败命令和实际结果定位问题。可恢复的局部问题由 MASTER 与原 WORKER 解决后从原步骤继续。需改变计划时由作者修订、MASTER 复核受影响步骤。待用户决策的任务保留原归属，其他 WORKER 继续。
- PR 交付按一份 RUNBOOK 一个 PR。以当前 PR 的 HEAD、冲突、CI 和审查线程为准派回原 WORKER。共享边界的任务按已传达的合入顺序推进。全流程内各阶段沿用启动授权。若用户提前合入了另一项，按实际最新主线重算先后，由后合入的 WORKER 复验受影响的共享边界。
- 核实合并提交在目标分支后，更新自己的本地 Git checkout和空闲 WORKER。在途 WORKER 在 STEP 已提交的安全点纳入新主线，解决交叠并复验受影响行为。保留用户改动和无关分支。清理只涵盖本任务且已确认合入的分支。
- 启动时可记录用户指定的外部检查观察期限，并传给 WORKER。已在运行的 CI 或 Codex 在期限内持续跟踪。明确外部阻断或期限到达时，记录 PR、HEAD、检查状态和恢复条件，保留原归属并推进其他任务。恢复时重新回读原 PR，HEAD 变化则按当前 HEAD 核验。期限到达只改变调度状态。
- 每次同步后根据交付收口核对结果更新待派范围。持续为已收尾、已同步且空闲的 WORKER 派工。有在途动作可产生下一步所需证据时，继续跟踪到结果或既定等待边界。

### 完成与阻断

- **完成**。全流程以授权范围内的全部适用正式需求为完成条件。对照最新目标分支逐项核对 Readiness 已达「已实现」、必需验收有可回读的证据、相关交付已合入并收尾，才可宣告完成。用户限定阶段时按指定阶段收口，保留剩余需求的实际状态。
- **继续推进**。只要还有未完成的适用需求，按需求编号核对在途任务和待派候选，先做授权内能推进的下一步。T0 STOP 限制实施和实栈启动，已交回的草稿仍按实际 blob 送审，并继续可做的补查、草稿修订与验收准备。现有目录受阻时，按「绑定与派工」继续筛选候选，并为符合条件的任务新建隔离的本地 Git checkout后派工。
- **本轮阻断**。只有核对完全部未完成的适用需求、完成可自主推进的工作，且剩余动作均依赖尚未满足的外部条件时，才可结束本轮并报告阻断。按需求或共享阻断记录已做的工作、阻断证据、所需输入或决定、由谁或何种事件解锁，以及恢复后的第一步。恢复时从实际状态接续。
