# Bento RUNBOOK Worker

用户或 MASTER 可显式调用 `$bento-runbook-worker <RUNBOOK 文件名>`。读取 [RUNBOOK Rules](../../../docs/00-governance/RUNBOOK-RULES.md)、[提交规则](../../../docs/00-governance/COMMIT-RULES.md)和 [PR 规则](../../../docs/00-governance/PR-RULES.md)。起草和修订按 MASTER 单独派发的阶段执行。

## 启动与恢复

- 用户直接显式启动全流程时，授权范围包括指定 RUNBOOK 的实施、逐步提交、推送、开一个 PR、转 Ready、处理 Codex 意见、满足门禁后合并、同步和清理已合入的任务分支。MASTER 派工时继承其传达的用户授权。用户在调用中指定的更窄阶段或限制优先。起草、审核和仅提交 RUNBOOK 的任务按该阶段收口。
- 在指定 checkout 的 `docs/30-designs/` 找到 RUNBOOK。核对分支、基线和已审核的 RUNBOOK 提交。T0 由作者或维护者在执行前完成，WORKER 核对通过证据。有共享代码、状态或测试资源时核对 MASTER 确认的顺序和窗口。现有改动归属明确后再开始，保留暂停现场和用户文件。
  恢复前读取最后成功提交和实际 PR 状态，再选择入口。

| 已核实的状态                        | 下一动作                                                                             |
| ----------------------------------- | ------------------------------------------------------------------------------------ |
| 无 PR，最后提交中仍有 RUNBOOK       | 从首个剩余 STEP 继续。若工作区已删掉该步但尚未提交，按下节的提交失败规则恢复同一步。 |
| 无 PR，最后一步已提交且删除 RUNBOOK | 从 PR 交付继续。                                                                     |
| PR 开放                             | 跟踪原 PR，按其当前 HEAD 继续。                                                      |
| PR 已合并                           | 核对合并提交并执行本地收尾。                                                         |
| 状态不一致或无法核实                | 保留现场，报告冲突的证据。                                                           |

## 执行与本地提交

1. 从 T1 或首个剩余 STEP 开始。核对前置条件和允许操作的文件。每步最多涉及 10 个不同文件，包含 RUNBOOK 及专门核对的文件。
2. 执行本步操作和规定验证。仅当命令退出状态、实际执行的测试范围和所有规定断言都满足时，记为 `PASS`。记录 STEP、命令、实际结果及对应的代码状态。缺少断言结果、测试被跳过或证据对应其他版本时，按 RUNBOOK 处理，本步仍待完成。
3. PASS 后删除本步说明。保留剩余编号，把对已删步骤的依赖改为可核验的前置事实。最后一步把实际验证和未覆盖项写入 Readiness，并删除整个临时 RUNBOOK。
4. 核对暂存文件只包含本步产物和 RUNBOOK 变化，再做一次本地提交。回读新 SHA、提交文件清单及提交中的剩余步骤或最终删除。核对通过后进入下一步。
5. 提交失败时留在本步。产物仍与 PASS 证据一致时重试同一次提交。产物有影响验证的变化时，重跑受影响检查再提交。

STOP 时保留当前步骤和现场，报告最后完成的 STEP、对应提交、失败条件、复现命令、脱敏结果和所需决定。向 MASTER 回报，无 MASTER 时直接报告用户。按原范围修复可恢复问题并重验当前步骤。计划、范围或正式依据需要变化时，交回作者修订和审核。收到暂停指令时停止继续修改，在可确认的安全点报告工作区和仍在运行的命令。

## PR、审查与收尾

1. 核对授权、Readiness 和相对目标分支的完整差异，推送并创建或恢复同一个 PR。回读编号、base、head、草稿状态和检查。通常先开 Draft。当前分支的本地验证通过且 PR 差异范围核对后可转 Ready，已触发的必需 CI 有失败时先处理。回读 Ready 状态。按照仓库实时门禁列出必需检查，并把检查结果对应到当前 HEAD。缺失、排队和在途保持等待。失败时定位原因并修复，取消或可恢复的运行故障按原因重跑。出现合并冲突时同步目标分支、解决冲突并复验受影响行为。推送后重新回读当前 HEAD 的结果。
2. 每个 PR 必须取得 **当前 HEAD 的明确 Codex 审查结论**。依据可核实的 Codex 审查结果、review summary 和关联的 findings 判断；反应只有能对应当前 HEAD 时才可作为证据。无信号、在途、读取失败或额度不足都保留待审状态。CI 通过也不能代替 Codex 审查结论。用约 60 秒间隔观察。确认当前 HEAD 没有已触发的审查且允许请求审查时，发一次审查请求并记录对应 HEAD。Codex 明确不可用或达到启动时给定的观察期限时，回报 PR、HEAD、最近检查结果及恢复条件，保持待审。未设期限且检查仍在运行时继续观察。恢复后重新读取原 PR，按当前 HEAD 判断。
3. 有 finding 时按 [评论处理 Skill](../bento-codex-comment-fix/SKILL.md) 处理。全流程授权涵盖本 PR 的处理，按其显式调用方式启动。逐项记录修复或有依据的拒绝，核对回复和线程状态。暂缓或待决仍是未收口。新提交重新等待当前 HEAD 的明确 Codex 结论和必需 CI。该 Skill 达到本轮处理上限时，向 MASTER 报告尚余 finding。
4. 合并前回读 PR 的当前 HEAD、目标分支、必需 CI、Codex 审查结论、有效反馈、合并顺序及 [远端门禁](../../../docs/00-governance/PR-RULES.md#main-branch-protection)。目标分支变化时按约定同步并复验共享边界。全部满足且属于本轮合并授权时，以本次核对的 HEAD 为前提执行合并，并回读合并提交。若执行时 HEAD 变化，重新核对。
5. GitHub 回读为已合并且合并提交已进入目标分支后，记录 PR、目标分支和合并提交，供 MASTER 同步。随后快进自己的 checkout，核实任务分支 tip 已纳入目标分支，按授权清理对应本地或远端分支。保留无关改动与历史 stash。最后回报 PR、合并提交、同步基线、审查及 CI 状态、分支清理结果、未覆盖项和是否空闲。跨聊天主动回报按用户授权执行，MASTER 也可通过本聊天的回报和 Git 状态跟进。
